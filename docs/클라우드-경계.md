# 클라우드 경계 — 급식 시스템이 GCP를 다시 쓸 때

> 2026-08-02 결정. **급식이 GCP 리소스를 만들어야 할 때 이 문서를 먼저 연다.**

## 지금 상태

급식 시스템은 GCP를 쓰지 않는다.

```
급식 정산   Vercel + Supabase
급식 비교   Vercel + Supabase
```

2026년 2월에 `preschool-app`을 챗봇 프로젝트(`first-counsulting-rag-chatbot`)의
Cloud Run에 얹어 배포한 적이 있는데, Vercel로 옮긴 뒤에도 방치돼 있었다.
2026-08-02에 정리했다. 그 뒤로 급식의 GCP 리소스는 0이다.

## 규칙 — 첫 리소스부터 별도 프로젝트

**급식 시스템이 GCP 리소스를 하나라도 만들어야 하면, 그 첫 번째 것부터
별도 프로젝트에 만든다.** 남의 프로젝트에 얹지 않는다.

### 왜 — 거래명세표와 같은 원칙이다

`docs/systems/settlement/조정.md §19`에서 이미 같은 판단을 했다.

> 유치원마다 파일을 따로 만든다. 한 파일에 여러 곳을 담으면 다른 유치원 단가가 섞인다.

한 파일에 담고 "섞이지 않게 조심하자"고 약속할 수도 있었다. 그러지 않은 이유는
**나누면 조심할 필요가 없기 때문**이다. 클라우드도 같다.

```
합의   "정책 바꿀 때 서로 알려주자"   → 사람이 바뀌거나 잊으면 무너진다
구조   남의 정책이 닿지 않게          → 알릴 일 자체가 없다
```

### 실제로 겪은 일

챗봇 프로젝트에 건 Artifact Registry 정리 정책은 **저장소 단위**라 앱을
구분하지 않는다. 급식 이미지 15개가 남의 정책 아래 놓였다. 실제로는
`keepCount`가 패키지별로 적용돼 위험하지 않았지만, **위험 여부를 그때그때
확인해야 한다는 것 자체가 비용**이었다. 봇 두 대가 반나절을 썼다.

### 저장소만 나누는 건 어중간하다

같은 프로젝트에 저장소만 따로 만들면 정책은 갈리지만 **IAM·로그·할당량·
API 키가 그대로 공유**된다. 절반짜리 분리라 결국 같은 문제가 다른 얼굴로 온다.

## ⚠️ 비용 절감이 목적이 아니다

Artifact Registry 무료 0.5GB는 **프로젝트가 아니라 청구 계정 단위**다
([Google Cloud 요금](https://cloud.google.com/artifact-registry/pricing)).
프로젝트를 나눠도 한도는 안 늘어난다.

목적은 두 가지다.

- **책임** — 누가 정하고 누가 치우는지가 명확해진다
- **가시성** — GCP는 청구서를 프로젝트별로 나눠 보여준다. 26년 7월 청구서에서
  `Project RAG Chatbot ₩13,371`처럼 한 줄로 잡혔다. 급식 비용도 따로 보인다

## 언제 그날이 오나

현실적인 계기는 셋이다. 2026-08-02 기준 셋 다 아니다.

- **말일 정산 자동화** — 월말 배치를 서버에서 돌리게 되면 Cloud Run Jobs + Scheduler
- **엑셀 생성이 Vercel 함수 한도에 걸릴 때** — 지금은 여유가 있다
  (거래명세표 335KB 생성이 몇 초)
- **원천 파일 OCR** — 신세계·CJ가 PDF로 주기 시작하면 Document AI
