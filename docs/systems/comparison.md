# 급식 거래명세서 비교 시스템 (`[비교]`)

> **운영 중 · 95% 완성.** 비정기 사용. 신규 기능보다 **안정성이 최우선**.
> 정산 시스템 개발이 이 시스템을 깨뜨리면 안 됩니다.

## 1. 목적

유치원이 현재 쓰는 급식업체 거래명세서를 업로드해, **신세계푸드 단가와 비교**하여
절감액을 산출하고 원장 제출용 제안서·영업자 손익 보고서를 만든다.

**비교 대상 공급사는 신세계 1곳뿐**이다. (CJ는 정산 시스템에서만 등장)

## 2. 위치와 접근 권한

- 화면: `src/app/calc-food/` — **경로 이동 계획 없음.** 운영 중이라 URL을 바꾸면
  북마크가 깨진다. `/app/*` 아래로 옮기는 건 실익이 없다.
- 도메인 로직: `src/lib/` (spec-parser, unit-conversion, matching-kpi, partner-profit,
  `funnel/`)

| 층 | 무엇 | 어디 |

데이터를 다루므로, 화이트리스트 안에서도 지정한 사람만 보도록 좁혔다.

뿐이다. URL을 직접 쳐도 위 2층에서 막힌다. (`comparison-reveal.tsx`, `clicks >= 3`)

### 배포 버전 표시 (2026-07-31)

화면 제목 옆에 `COMPARISON_VERSION`이 뜬다. **비교 시스템이 실제로 바뀐 커밋**의
날짜·시각이며, 정산만 고친 배포에서는 값이 그대로 남는다.
판별 경로는 `scripts/generate-version.mjs`가 정본이다 (settlement.md §16).

```

## 4. 핵심 규칙 (건드릴 때 주의)

- **확정은 매칭이 있어야만 가능** (`src/lib/confirm-guard.ts`). 무매칭 Enter = 확정 없이 다음으로.
  세션 로드 시 과거 오염 데이터 자가치유.
- **공급율(supplyRate)** 은 매칭 화면과 보고서가 **공유**한다 (`useSupplyRate` 훅,
  `proposal_extras.supply_rate`, 기본 1.25). 양쪽 절감액이 같은 값이어야 한다.
- **per-item 반올림**: 모든 합계는 `Σ Math.round(item)`. 카테고리 카드 합 == 헤드라인 절감액.
  순손실 카테고리도 **음수 그대로 표시**(clamp 금지).
- **단위중량 파싱**(`spec-parser.ts` + `invoice-unit-weight.ts`): 명세서마다 양식이 다르다.
  - 규격 선두 `[냉동]`·`[실온]` 등 **보관조건 태그 제거 후** 발주단위 판별
  - 규격이 KG/PK/BOX를 담으면 **규격 우선**(coarse한 `extracted_unit`이 덮어쓰지 못하게)
  - `Xg*Nea`는 곱함, 단 `.../BOX`(박스 묶음수)면 곱하지 않음
  - 개당 무게 범위는 **평균** 사용
- **품목군별 허용 오차**(`funnel/price-cluster.ts`): 농산물 ±40% / 축산물 ±25% /
  가공품 ±20% / 기타 ±30%. 농산물은 계절 변동이 커서 넓고, 가공품이 ±40% 차이나면
  다른 물건이다. 규격을 못 읽어도 **후보에서 버리지 않고** 순위만 뒤로 민다 —
  버리면 검수자가 손으로도 못 고른다.

### 네이버 쇼핑 검색 API 중단 (2026-08-15 확인)

같은 키·같은 헤더로 검색 하위 API 11개를 전수 호출한 결과:

```
blog news encyc cafearticle kin webkr image local  → HTTP 200
shop book doc                                     → HTTP 404  SE05
```

**키·URL 문제가 아니다.** 틀린 키로 부르면 401(코드 024)이 뜨고, 우리 키로
부르면 **인증을 통과한 뒤** 404가 난다. 권한 문제라면 401이어야 한다.
`.xml` 변형도 같다. 즉 네이버가 그 API를 서비스하지 않는다.

**공식 공지로 확정됐다** (2026-08-15 확인):

```
공지 32530 (2026-06-29)  Search API·Search Trend·Shopping Insight → NAVER API HUB 이관
                         단 쇼핑·책·전문자료는 이관 제외
공지 32564               검색 쇼핑/책/전문자료 API 종료 — 2026년 7월 31일(금)
```

> "해당 API는 유예 기간이 적용되지 않으며, 2026년 7월 31일 이후에는 **기존 발급
> 키를 포함하여 호출이 불가**합니다. **NAVER API HUB를 포함한 별도의 대체 API는
> 제공되지 않으니** 이 점 유의하시기 바랍니다." — 공지 32530

즉 **대체 API가 없다.** 수동 검색이 임시방편이 아니라 최종 답이다.
(`naver-openapi-guide` GitHub 미러에는 아직 "제공 중"으로 적혀 있다 — 믿지 말 것.)

⚠️ **나머지 검색 API(blog·news·image 등)도 2027-06-30에 개발자센터 지원이
끝난다.** 그 뒤에는 NAVER API HUB(NCP 계정·별도 키)에서만 쓴다. 지금은 shop만
썼으므로 당장 할 일은 없지만, 참고 카드를 되살리려 다른 검색 API를 붙일 때는
개발자센터가 아니라 API HUB에 등록해야 한다.

**대응** — 원래 이 카드가 자동화하려던 게 "품명을 네이버에서 검색 → 이미지
확인 → 시중가 점검"이었으므로, 그 수동 작업으로 되돌려 줬다.

```
naverShoppingSearchUrl   새 탭으로 네이버 쇼핑 검색을 연다 (검색어는 입력창 값)
describeNaverError       원본 JSON 대신 사람이 읽는 문장 + permanent 플래그
```

`permanent`면 화면이 **"다시 검색"을 감춘다** — 404/SE05는 몇 번 눌러도 같은
결과라 재시도 버튼은 거짓 희망이다. 중단 사실은 모듈 변수로 한 번만
확인한다(품목 200개마다 헛클릭하지 않게).

#### ⚠️ 링크 대상은 `search.naver.com`이다 — 쇼핑 전용 도메인이 아니다

처음에 `search.shopping.naver.com`을 넣어 배포했고, 검수자 화면에서
**차단 페이지**가 떴다. 실측:

```
search.shopping.naver.com/search/all?query=…       418 · "접속이 일시적으로 제한"
search.shopping.naver.com/…&frm=NVSCTAB            CAPTCHA "보안 확인을 완료해"
search.naver.com/search.naver?where=shop&query=…   200 · 네이버 가격비교 정상
```

차단 페이지가 사유로 "상품 구매, 탐색과 무관한 **외부 이벤트를 통한 접속**"을
든다. 우리 링크가 정확히 그것이다. 네이버 자신의 쇼핑 탭도 같은 도메인으로
가지만 `frm=NVSCTAB` + naver.com 리퍼러가 붙는데, 우리는 `rel="noreferrer"`이고
그래도 CAPTCHA가 떴다.

통합검색은 막지 않고 **네이버 가격비교** 섹션에 시중가가 나온다(실측:
`지리산 건조 취나물 200g 26,000원 · 배송비 4,000원`). 시중가 확인이라는
목적에는 충분하다. `search.shopping.naver.com`으로 되돌리지 말 것 —
테스트(`naver-shopping.test.ts`)가 막고 있다.

★ **원본 응답 본문을 화면에 흘리지 않는다.** 이전에는 120자를 그대로 보여 줘서
검수자가 `{ "errorCode": "SE05" }`를 봤다. 그걸 보고 할 수 있는 일이 없다.
정규화 계층(`normalizeNaverItems`)은 남겨 뒀다 — 대체 API를 붙일 때 재사용한다.

## 9. 신세계 단가 기준월 (2026-08-14 합의, 미착수)

세션을 시작할 때 **몇 월 신세계 단가로 비교할지** 고른다. 매칭·절감액이 그 달
단가를 쓴다.

### 먼저 알아야 할 사실 — `products`가 3개월 낡았다

`products`(비교 시스템의 신세계 DB)와 정산이 받은 월별 단가표는 **같은 데이터**다.
`standard_price` = 단가표 `결정단가`, `origin`·`order_deadline`·`supplier_partner`도 대응한다.

```
products 24,593행   SHINSEGAE 8,787(활성 7,964) · CJ 15,806
last_synced_at 5/9 이후 갱신  0건
```

8월 단가표와 대조한 결과:

```
코드 겹침 7,508 · products에 없는 신규 품목 320
단가 같음 6,273 · 다름 1,235   ← 16.4%가 틀렸다
  올랐는데 반영 안 됨 943 / 내렸는데 반영 안 됨 292
  평균 차이 17.5% · 최대 560%
```

⚠️ **틀린 것의 76%가 "실제로는 올랐는데 낡은 낮은 단가"** 다. 낮은 단가로 비교하니
**절감액이 과대 계상**된다 — 제안서에 부풀려진 숫자가 나갔을 수 있다.

### 설계 — 임베딩은 달마다 복제하지 않는다

`products`에 `period`를 붙여 월별로 만들면 8,000행 × 12개월 + 임베딩 96,000개가 된다.
**임베딩·search_vector는 품목명에서 나오고 품목명은 달마다 안 바뀐다.** 가격만 바뀐다.

```
products              품목이 존재하는가 + 어떻게 찾는가   (달과 무관)
                      embedding · search_vector · ppu · 규격파싱
shinsegae_price_book  그 달에 얼마인가 + 원산지          (월별 이력, migration 061)
```

### 바꿀 지점은 API 5곳뿐

`standard_price`가 UI 12개 파일에서 읽히지만, UI는 **API가 준 상품 객체를 그대로
쓴다.** API 경계에서 단가만 그 달 값으로 덮으면 UI는 한 줄도 안 고친다.

```
/api/products/search      매칭 후보 검색
/api/products/[id]
/api/products/last-sync
/api/sessions/[id]        세션 로드 시 확정 매칭
src/lib/matching.ts       AI 추천
```

### 세션에 기준월을 굳힌다

`audit_sessions.price_book_period` (nullable) 한 칼럼.

```
NULL      → 지금까지처럼 products.standard_price   (기존 세션 18개)
'2026-08' → 그 달 price_book 단가
```

⚠️ **기존 세션은 그대로 둔다** (2026-08-14 결정). 이미 제출한 제안서의 숫자가
나중에 바뀌면 안 된다 — 정산의 마감 스냅샷과 같은 원리다.

⚠️ **매칭을 시작한 뒤에는 기준월을 못 바꾼다.** 중간에 바꾸면 확정한 항목과 새 항목이
다른 달 단가를 쓴다. 바꿔야 하면 새 세션을 만든다.

### 그 달에 없는 품목은 후보에서 버리지 않는다

§4 원칙 그대로다 — 버리면 검수자가 손으로도 못 고른다. 대신 `8월 단가표에 없음`
배지를 붙여 검수자가 판단하게 한다. 억지로 다른 달 단가를 끌어오면 **조용히 틀린
절감액**이 나온다.

### 작업 순서

```
1. 단가표 코드를 features/shared/price-book으로 이동
   (AGENTS.md — settlement ↔ comparison 직접 import 금지)
2. migration 062: audit_sessions.price_book_period + products 신규 320개 upsert
3. API 5곳 단가 치환 (NULL이면 기존 동작 그대로)
4. 화면: 업로드 **앞에** 기준월 선택 + 세션 목록·리포트에 표시
5. 검증: 기존 세션 18개 절감액이 한 원도 안 바뀌는지 대조
```

⚠️ **임베딩은 기존과 같은 모델이어야 한다.** 다른 모델로 만들면 그 320개는 벡터
공간이 어긋나 검색에서 엉뚱하게 뜬다. 착수 전에 기존 생성 코드의 모델명·차원을 확인한다.

8월 단가표에 없음   36건 (7.5%)   버리지 않고 배지만
같은 항목 절감액   6,554,360 → 6,547,974  (-6,386원, -0.1%)
```

⚠️ **총 절감액은 거의 안 움직인다.** 오른 품목과 내린 품목이 상쇄된다.
계획을 세울 때 "절감액 과대 계상"을 근거로 삼았는데, **집계 수준에서는 0.1%**다.
가치는 다른 데 있다 — **품목별 단가가 40%나 달라지므로**, 유치원에 건네는
품목별 표가 맞아진다. 그리고 "언제 단가와 비교한 것인가"가 세션에 남는다.

## 10. 다중 원본 공급사와 확정 매핑 학습 (migration 064)

### 공통 데이터 구조

세션은 유치원 1곳의 비교 작업이고, `comparison_sources`는 그 세션에 들어온
거래명세표 묶음이다. 품목은 `audit_items.source_id`로 원본 묶음에 연결한다.

```
audit_sessions (유치원·비교 기준월)
  └─ comparison_sources (원본 공급사·파일·해시·최초/추가 여부)
       └─ audit_items (품목·추천 출처·최초 추천 상품)
```

- 공급사가 다르면 날짜·품명·규격·금액이 같아도 별도 거래로 보존한다.
- 같은 세션에 같은 파일 내용(SHA-256)을 다시 올리는 것만 차단한다.
- 추가 업로드는 엑셀 1개 또는 같은 공급사의 PDF·이미지 여러 개를 지원한다.
- 기존 품목·확정 매칭은 다시 분석하지 않고 새 `source_id`의 품목만 추가한다.
- 화면은 `이번 추가분` 필터와 원본 공급사 배지를 제공한다.

### 사용자 결정 학습

`comparison_match_events`는 추천·선택·확정·전파·제외·해제 이력을 보존하고,
`comparison_match_evidence`는 품목별 최종 확정 1건을 정본으로 둔다. 반복해서
확정해도 횟수가 부풀지 않으며, 상품 변경·비교불가·해제 시 집계를 증감한다.

추천 우선순위는 다음과 같다.

```
현재 세션의 동일 서명 확정
  > 같은 원본 공급사의 과거 확정
  > 공급사 불문 과거 확정 2회 이상
  > 기존 검색·규칙 알고리즘
```

서명은 `품명 + 규격 + 원산지 + 단위`를 정규화해 비교한다. 같은 우선순위의
두 상품이 최다 확정 동률이면 과거 결정을 승계하지 않는다. 학습 결과는 후보
1위로만 올리고 **자동 확정하지 않는다**. 검수자가 확정해야 다음 학습 근거가 된다.

`recommendation_source` 값과 화면 표시는 다음과 같다.

- `algorithm`: 기존 검색·규칙 추천
- `session_exact`: 현재 세션 확정 승계
- `history_supplier`: 공급사 학습
- `history_global`: 과거 확정

운영 품질은 이벤트 정본으로 Top 1 유지율, 후보 내 정답률, 추천 출처별 수락률,
사용자 변경률을 측정한다. 배포 전에는 migration 064 적용 후 기존 확정 결과의
전역 기억 이관 건수와 품목별 최종 근거 건수가 일치하는지 확인한다.

## 11. 제안서 발행·변경 이력과 월간 보고서 (migration 065)

제안서 건수는 다운로드 클릭 수가 아니라 **한 비교 세션에서 유치원 제출용
제안서를 발행한 버전 수**로 집계한다. PPTX 파일 생성 성공 또는 PDF/인쇄
대화상자 시작 시 발행 이력을 기록한다. 브라우저는 실제 PDF 저장 완료 여부를
알 수 없으므로 `pdf_print`는 인쇄 시작 기록임을 보고서에 명시한다.

`comparison_proposals`는 세션별 정본 1건, `comparison_proposal_versions`는
발행 시점별 불변 스냅샷이다. 발행 저장은 DB 함수에서 세션 단위 advisory lock을
잡고 처리하므로 동시 클릭에서도 버전 번호가 중복되지 않는다. 각 클릭의
`idempotency_key`가 같으면 기존 결과를 반환해 네트워크 재시도 중복도 막는다.

거래명세표 변경은 서버가 `audit_items`와 `comparison_sources`에서 다시 만든다.
클라이언트가 해시를 제출하지 않는다. 다음 필드를 정규화한 뒤 행 순서와 파일명은
무시하고 SHA-256으로 비교한다.

```
원본 공급사 + 품명 + 규격 + 원산지 + 단위 + 수량 + 단가 + 공급가 + 세액 + 합계
```

공급사가 다르면 나머지 값이 같아도 다른 거래다. 재발행은 직전 버전과 비교해
`명세+금액 변경 / 명세만 변경 / 금액만 변경 / 변경 없음` 네 유형으로 집계한다.
금액 변경 기준은 제안서에 표시된 **월 제안금액의 정확한 값**이며, 증감 근거에는
기존금액·제안금액·절감액·공급율·부가서비스 차이를 함께 저장한다.

월간 엑셀은 한국시간 발행일 기준이며 `월간 요약`, `제안서 버전 이력`,
`거래명세표 변경 상세`, `제안금액 변경 상세` 4개 시트로 만든다.

과거 데이터에는 다운로드 로그가 없으므로 확정 실적으로 위장하지 않는다.
`scripts/backfill-comparison-proposals.ts`가 아래 근거로 추정하고 모든 행에
`historical_estimate`와 신뢰도를 저장한다.

- 높음: 보고서 단계와 `proposal_extras`가 모두 있음
- 보통: 보고서 단계만 있음
- 낮음: `proposal_extras`만 있음

과거 금액은 현재 보존된 확정·비교포함 품목, 신세계 매칭 단가, 당시 저장 공급율과
부가서비스로 재구성한다. 이는 당시 실제 파일의 완전한 복원이 아니라는 점을
`estimate_basis`에 남긴다. 드라이런은 기본 실행, 실제 반영은 `--apply`일 때만 한다.

migration 065는 기존 운영 테이블을 수정하지 않고 신규 테이블과 함수만 추가한다.
장애 시 앱을 직전 커밋으로 되돌리는 것이 우선이며, 데이터 폐기가 꼭 필요할 때만
백업 후 `supabase/rollbacks/065_comparison_proposal_history.sql`을 실행한다.
