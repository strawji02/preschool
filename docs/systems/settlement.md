# 급식 정산 시스템 (`[정산]`)

> 신규 개발. 매월 최소 1회 정기 사용 → 지속적 DB 관리 + 월 마감.
> 근거 문서: `유치원급식_정산시스템 요구사항 정의서(SRS).docx`
> 근거 데이터: `정산시스템_개발용_급식_정산_종합_26년_6월분.xlsx` (실제 26년 6월 정산)

## 1. 목적

신세계·CJ에서 매월 받는 원천 데이터를 업로드해 **유치원 매출 청구**와 **영업자 정산**을 자동화한다.
현재 담당자가 엑셀에서 수작업(셀 병합·수기 열 추가)으로 하는 과정을 전부 시스템화한다.

## 2. 프로세스

```
원천 업로드(신세계·CJ) → 파싱·정규화 → 영업자-유치원 매핑
  → [매출] 과세/면세 분리 → 유치원 청구액
  → [정산] 마진 → 공제 → 3.3% → 영업자 지급액
  → 엑셀 3종 출력 (홈택스 / 영업자 / 세무사)
```

## 3. 정산 산식 ★ (실제 엑셀 수식에서 추출, 역검증 완료)

집계 단위: **영업자 → 유치원(사업장)×식당**. 아래는 영업자별 합계 기준.

```
차액(총마진)  M = Σ(단가합계 − 원가합계)                    ← 총액(세액 포함) 기준
적립금(플랫폼) O = ROUNDUP((원가합계 − 원가세액) × 5%, -1)    ← 10원 올림
부가세차액     P = 단가세액 − 원가세액                       ← 영업자 전액 부담
사업자공제     Q = 매월 수기 입력 (커피차 등 부가서비스 비용)
지급액(세전)   R = M − O − P − Q

신고액         V = 영업자 유형에 따라 분기 ★
                 · 코파운더  → R + O   (적립금을 사업소득 신고액에 포함)
                 · 일반 파트너 → R      (신규 등록 파트너는 전부 일반)
소득세         S = ROUNDDOWN(V × 3%, -1)     ← 신고액(V) 기준, 10원 내림
지방소득세     T = ROUNDDOWN(S × 10%, -1)    ← 10원 내림
실지급         U = R − S − T                 ← 세전(R)에서 차감
```

- 총액차액 − 부가세차액 = 공급가 기준 차액 → SRS의 "공급가 기준 총마진"과 **수학적으로 동일**.
- 코파운더 3명: **김중영·이동현·조성곤**. 그 외 및 신규 등록자는 일반.
- 김중영은 과거 엑셀에서 원천징수 누락 → **시스템에서는 동일하게 원천징수 적용**.

## 4. 분할 신고

한 영업자의 사업소득을 **여러 명 명의로 나눠 신고**하는 운영을 지원한다.
- 배분은 **수기 입력**(성명 + 금액).
- **검증 필수**: 분할 합계 == 해당 영업자 신고액(V). 불일치 시 마감 차단.
- 실제 사례(26년 6월): 이동현 13,490,317 → 이동현 4,490,317 + 김인순 5,000,000 + 이유나 4,000,000.

## 5. 원천 데이터 구조

**신세계** (`신세계_전체 일반`, 536행) — 품목 단위, **2행 병합 헤더**
```
순번 | 사업장(코드,명) | 식당(코드,명) | 입고일자 | 카테고리 | 품목코드 | 품목명 | 규격 | 단위 | 면과세 | 수량
     | 납품(단가,금액,세액,총액)   ← 원가(매입)
     | 가맹점(단가,금액,세액,총금액) ← 유치원 청구(매출)
```

**CJ** (`CJ_전체 집계표`, 40행) — 사업장×식당 집계 단위, 1행 헤더
```
번호 | 사업장코드 | 사업장 | 식당코드 | 식당명 | 사업부 | 팀
   | 원가: 과세공급가, 과세부가세, 과세금액, 면세, 합계(a)
   | 단가: 과세공급가, 과세부가세, 과세금액, 면세, 합계(b)
   | 차액(b−a)
```

⚠️ **레벨이 다름** — 신세계는 품목, CJ는 집계. 공통 정규화 지점은 **사업장×식당×과세구분**.
신세계 품목 데이터는 이 레벨로 집계해서 CJ와 합산한다.

### 5-1. 사업장 = 유치원 1곳, 식당 = 품목 ★ (2026-07-30 실측)

양쪽 원천의 **의미가 같다.** 이게 전체 데이터 모델의 기준점이다.

| 원천 | 사업장 | 식당 |
|---|---|---|
| 신세계 | `[89890] EDU)키즈_국제유치원(키즈웰)` = 유치원 1곳 | `급식재료`, `교사식재료`, `종일반간식`, `오전간식`, `행사` |
| CJ | `[1005] 키즈웰에듀푸드(해밀유치원)` = 유치원 1곳 | `…(해밀유치원)`, `…_급식재료`, `…_간식보조금` |

- 신세계 4 사업장(본사 포함) + CJ 13 사업장 = **본사 1 + 유치원 16** → 홈택스 파일의 16곳과 정확히 일치
- CJ 식당명은 유치원명을 반복해서 담고 있을 뿐, 구분자는 접미사다
- **따라서**: 사업자등록번호·상호 등 계산서 정보는 **사업장(=유치원)** 에 붙이고,
  품목명은 **식당** 에 붙인다. 별도 유치원 테이블은 필요 없다.
- 한 유치원이 두 원천에 걸치는 경우는 26년 6월에 없다. 생기면 **사업자번호로 묶어**
  계산서를 합친다 — (source, business_code)로 묶으면 안 된다.

**품목명은 식당명에서 기계적으로 나오지 않는다 → 마스터에 저장해야 한다**

식당명 51건 중 15건은 품목 문자열을 포함하지 않고, 포함해도 표기가 다르다:

| 식당명 | 실제 품목 |
|---|---|
| `키즈웰에듀푸드(선경유치원)` (접미사 없음) | `급식재료` |
| `키즈웰에듀푸드(젬마유치원_수익자)` | `급식재료(수익자)` |
| `키즈웰에듀푸드(부산_복자유치원_식재료(교원))` | `급식재료(교직원)` |
| `국제유치원(키즈웰) 행사` | `행사용` |
| `키즈웰에듀푸드(복자유치원_방과후간식재료)` | `방과후간식` |

`(해밀유치원)` 39,490 + `(해밀유치원_급식재료)` 96,650 = **급식재료 136,140** 1장

**(유치원 사업자번호 × 품목 × 과세구분)** 이다.

금액 기준으로 식당→품목을 역추적하면 **89건 중 87건이 유일 매칭**되고, 남은 2건이
위 해밀 합산 사례다. 이 결과를 시드로 쓰되 사람이 한 번 검토한다.

## 7. 개인정보 방침

- **주민번호는 저장하지 않는다.** 지급명세서에 빈칸으로 출력 → 사용자가 다운로드 후 별도 처리.

## 8. 월 마감

상태: `작성중 → 확정 → 마감`

- 마감 전 검증: 분할 신고 합계 일치, 매핑 누락 없음.

## 9. 수금 관리

- 유치원별 **입금일자만 사용자 수기 입력**.
- 한 영업자가 담당하는 **모든 유치원 입금이 완료되면** → 해당 영업자 지급 요청 **알림**.
- 미수금(잔액) = 청구합계 − 수금액.

### 확정된 것 (2026-07-29)

**세전 정산액이 음수일 때 → 0 처리 + 경고.**
받을 게 없는 달이므로 신고할 사업소득도 없다고 본다. 코파운더라도 적립금을 신고액에
넣지 않는다(0 처리가 우선). 원래 음수값은 `preTaxRaw`에 보존하므로, 이월 정책이
정해지면 거기서 이어가면 된다. 조용히 0으로 만들지 않고 반드시 경고를 남긴다.

**정산 대상이 아닌 사업장(본사 등) → 명시적 `정산제외` 표시.**
매핑 누락과 반드시 구분한다 — 섞이면 "마감 전 매핑 누락 없음" 검증이 무의미해진다.
`settlement_venues.is_excluded`로 표시하고, 매핑값은 세 상태를 갖는다:

## 13. 경영 보고서 (설계 — 2026-07-30)

### 13-1. 설계 원칙

**세 가지 기준을 섞지 않고 나란히 놓는다.** 섞으면 "장부상 이익은 났는데 통장에
돈이 없다"를 설명할 수 없다.

| 기준 | 무엇을 답하는가 | 근거 |
|---|---|---|
| **발생(거래)** | 이번 달 얼마 팔고 얼마 사왔나 | 원천 업로드 = 확정값 |
| **세무(신고)** | 언제 얼마를 세무서에 내나 | 부가세·원천세·사업소득 |
| **현금(입출금)** | 통장에 실제로 얼마 남나 | 수금일·지급일 **수기 입력** |

**금액은 총액(세금 포함)이 기본, 공급가는 토글.** 산식의 M·P가 총액 기준이고
(§3), 수금·지급도 총액이라 총액이 업무 언어다. 공급가는 부가세 검산용으로만 쓴다.

### 13-2. 화면 3단 (26년 6월 실값)

**① 매출·매입 — 거래 기준**

```
매출(유치원 청구)  102,346,907 = 면세 65,846,245 + 과세공급가 33,182,420 + 세액 3,318,242
매입(신세계·CJ)     74,009,016 = 공급가 … + 세액 2,413,235 + 면세 …
총마진 M            28,350,816
```
- 유치원 16곳 × 품목별 드릴다운, 공급사별(신세계/CJ) 매입 분해
- 마진율 표시: 매출 대비 27.7%
- ⚠️ 매출에서 **정산제외 사업장(본사)을 뺀다** — 계산서를 발행하지 않으므로

**② 영업 파트너 — 마진이 어떻게 쪼개지는가**

영업자별 워터폴 `M → −O → −P → −Q → R → −3.3% → U`

| | 합계 |
|---|---|
| 총마진 M | 28,350,816 |
| 적립금 O (플랫폼 5%) | 3,579,360 |
| 부가세차액 P | 905,912 |
| 사업자공제 Q | 2,320,500 |
| 영업자 세전 R | 21,542,074 |
| 원천세 (3.3%) | 531,960 |
| **영업자 실지급 U** | **21,010,114** |
| **본사 몫** | **6,808,742** |

본사 몫 = O + P + Q + 본사 자체 마진 2,970 → 항등식이 닫힌다.
**이게 회사의 실질 수익이다** — 매출총이익(M)이 아니라 이 숫자를 헤드라인으로 쓴다.

**③ 월 마감 재무 요약**

세금 3종을 각각 분리한다 (성격·납부시점이 다르다):

| 세금 | 계산 | 26년 6월 | 납부 |
|---|---|---|---|
| 부가가치세 | 매출세액 − 매입세액 | 3,318,242 − 2,413,235 = **905,007** | 분기 신고 |
| 원천세 | 소득세 + 지방세 | **531,960** | 익월 10일 |
| 사업소득 | 영업자 개인 신고 | 16,120,927 (신고액) | 지급명세서 제출 |

현금흐름:
```
유입  유치원 수금        102,346,907
유출  신세계·CJ 대금      74,009,016
      영업자 실지급       21,010,114
      원천세                 531,960
      부가세                 905,007
순현금                     5,890,810
```

⚠️ **부가세차액 회수액(905,912)과 실제 납부액(905,007)이 905원 다르다.**
본사 자체 매입세액 905원은 공제받지만 어느 영업자에게도 부담시키지 않아서다.
보고서에 대조 행으로 남겨 매달 확인한다 — 조용히 넘기면 누적된다.

### 13-3. 발생 vs 현금 (§9 수금 관리와 연결)

- 미수금 = 청구합계 − 수금액 (유치원별 입금일자 수기 입력)
- 미지급 = 실지급액 − 지급완료액 (영업자별 지급일)
- **영업자 담당 유치원 전원 입금 완료 → 지급 요청 알림** (§9)
- 보고서 상단에 `발생 순이익 6,808,742 / 현금 순증 5,890,810` 를 나란히 놓고
  차이를 미수금·미지급으로 설명한다

### 13-4. 확정 (2026-07-30, 사용자 확인)

**본사 사업장 12,925원 = 마케팅비.** 원가 9,955원이 마케팅 비용이고,
단가 12,925 / 차액 2,970은 **손익에 넣지 않는다** — 내부 대체 금액이고 계산서도 없다.

이렇게 처리하면 항등식이 정확히 닫힌다 (유령 마진과 905원 차이가 동시에 해소된다):

```
매출              102,346,907   ← 계산서 발행분 (본사 제외)
매출원가           73,999,061   ← 전체 매입 74,009,016 − 본사 9,955
총마진 M           28,347,846   = 영업자 4명 차액 합계와 원단위 일치
− 영업자 세전 R    21,542,074
= 본사 몫           6,805,772   = 적립금 3,579,360 + 부가세차액 905,912 + 공제 2,320,500
− 마케팅비              9,955
= 영업이익          6,795,817
```

**부가세 905원 차이는 이상 항목이 아니었다.** 회수액 P 905,912 − 납부액 905,007 = 905원은
**본사 마케팅비에 딸린 매입세액 공제분**이다. 보고서에는 대조 행으로 남기되 경고가 아니다.

**계산서는 현행 유지** — 품목마다 1장(16곳 → 88장). 품목1~4 슬롯은 쓰지 않는다.

**품목명은 화면에서 지정한다** — 신규 식당이 생기면 품목명을 입력해야 하고,
미지정이면 마감을 차단한다. §14 참고.

## 14. 신규 등록·수정·이관 (설계 — 2026-07-30)

매월 신세계·CJ 데이터로 정산을 시작할 때 **신규 유치원·신규 식당·신규 영업자**가
나타난다. 담당 이관도 생긴다. 이 절차가 무너지면 금액이 조용히 빠지거나
과거 정산이 재현되지 않는다.

### 14-1. 절대 원칙 — 과거 정산은 바뀌지 않는다

지난달 내역서를 다시 뽑았을 때 담당자나 금액이 달라지면 **지급 근거와 세무 문서가
흔들린다.** 두 가지로 막는다.

1. **월 마감 스냅샷.** 마감 시점의 매핑·영업자 유형·수수료율·사업자공제·분할신고를
   통째로 저장한다. 마감된 월은 현재 마스터가 아니라 **스냅샷으로 재생성**한다.
2. **이관은 월 단위로만.** 원천 데이터가 월 집계라 일할 계산이 불가능하다.
   `적용 시작월(YYYY-MM)`만 받는다. 월 중간 이관 개념은 두지 않는다.

### 14-2. 마감 차단 사유 3종 (매핑 누락과 같은 급)

| 사유 | 왜 막는가 |
|---|---|
| **담당 영업자 미배정** | 그 사업장 금액이 정산에서 조용히 빠진다 |
| **유치원 사업자 정보 미비** | 계산서를 발행할 수 없다 (사업자번호·상호·대표자·주소·이메일) |
| **식당 품목명 미지정** | 계산서 발행 단위(유치원×품목×과세구분)를 정할 수 없다 |

`정산 제외`는 이 셋과 **명시적으로 구분한다** (§11 확정 사항). 본사 마케팅비처럼
의도적으로 빼는 것은 경고를 내지 않는다.

### 14-3. 흐름 — 월 정산 안에서 인라인으로 해결한다

```
업로드 → 분석 → [미해결 항목] 그 자리에서 해결 → 자동 재분석 → 정산 → 마감(스냅샷)
```

**별도 마스터 화면으로 나가게 하지 않는다.** 담당자는 "왜 마감이 안 되지?"에서 막히고,
화면을 옮기면 맥락과 업로드한 파일을 잃는다. 파일은 이미 브라우저에 있으므로
저장 후 즉시 재분석한다.

미해결 항목 각 행에 액션 3개:
- **기존 유치원에 연결** — 같은 사업자번호의 새 식당. 담당 영업자를 자동 상속한다.
- **신규 유치원 등록** — 사업자 정보 + 담당 영업자 + 품목명
- **정산 제외** — 사유 선택(마케팅비/본사/기타)

모달이 아니라 **인라인 확장**으로 연다. 여러 건을 연속 처리해야 하므로 모달은 방해다.

### 14-4. 입력 안전장치

**사업자등록번호 — 체크섬 검증 (국세청 규칙)**

가중치 `[1,3,7,1,3,7,1,3,5]`를 앞 9자리에 곱하고, 9번째 자리 × 5의 **십의 자리를 더한** 뒤
`(10 − 합 % 10) % 10`이 마지막 자리와 같아야 한다.

실측: 우리 17개(본사 포함) **전부 통과**, 한 자리 오타 1,530가지 **100% 검출**.
국세청 진위확인 API(공공데이터포털)는 선택 사항 — 체크섬만으로 오타는 다 막힌다.

- 사업자번호가 **이미 등록돼 있으면** "복자유치원(1318208466)이 이미 있습니다 —
  같은 유치원의 다른 원천인가요?"로 유도한다.
- ⚠️ 상호 중복은 **정상**이다 (`복자유치원` 3곳). 중복 판정은 사업자번호로만 한다.
- 사업자번호 **변경은 수정이 아니라 신규 등록 + 이관**으로 안내한다. 사실상 다른 사업자다.

**품목명 — 오타가 계산서를 쪼갠다**

기존 23종을 빈도순 콤보로 제시한다 (`급식재료` 27건, `방과후간식` 20건이 압도적).
직접 입력은 허용하되 유사 항목을 경고한다: `급식재료 `(뒤 공백)을 넣으면
"기존 `급식재료`와 다릅니다 — 계산서가 2장으로 쪼개집니다".

**신규 영업자**

유치원 등록 폼 안에서 바로 만들 수 있게 한다(`+ 새 영업자`). 단:
- **유형은 `일반` 고정** (§3: 신규 등록 파트너는 전부 일반)
- 수수료율 5% 기본
- **코파운더 지정·수수료율 변경은 마스터 화면에서만** — 금액에 직결되므로 실수를 막는다

### 14-5. 이관 UI

- 진입점: 유치원 상세 또는 영업자 상세의 `담당 이관`
- 대상 유치원 다중 선택 → 새 담당자 → **적용 시작월**(기본: 다음 달)
- **이번 달로 소급하면 금액 영향을 미리 보여준다** — "A 실지급 −1,234,560 / B +1,234,560"
- 이미 마감된 월은 소급 불가. 재개 권한이 있어야 열 수 있다 (§8).
- 이관 이력을 유치원 상세에 타임라인으로 남긴다

### 14-6. 마스터 수정

유치원 정보는 **계산서에 그대로 찍힌다.** 변경 시 "다음 발행부터 적용됩니다"를 명시하고,
누가·언제·무엇을·이전값을 이력으로 남긴다 — 세금계산서 오류는 수정발행 사유가 되므로
추적이 필요하다.

### 14-7. 마감 전 체크리스트 (게이트)

```
□ 담당 영업자 미배정          0건
□ 유치원 사업자 정보 완비      (사업자번호·상호·대표자·주소·이메일)
□ 식당 품목명 지정 완료
□ 분할 신고 합계 일치
```

4개 전부 통과해야 `확정` → `마감`. 각 항목에서 해당 위치로 바로 점프할 수 있게 한다.

### 14-8. 스키마 추가 계획

- `settlement_venues`(=사업장=유치원)에 계산서 정보: `business_no`(체크섬 검증),
  `company_name`, `ceo_name`, `address`, `biz_type`, `biz_item`, `email1`, `email2`,
  `exclusion_reason`
- `settlement_venue_items`(=식당): `(source, business_code, restaurant_code)` →
  `invoice_item_name`
- `settlement_partner_transfers`: 유치원 × 이전 담당 × 새 담당 × `effective_from`(YYYY-MM)
- `settlement_closings` + 스냅샷 테이블: 마감 월의 전체 상태
- 마스터 변경 이력 테이블

### 14-9. 구현 순서

1. 스키마 + 26년 6월 시드 (홈택스 파일에서 추출 — 필드 불일치 0건 확인됨)
2. **홈택스 엑셀 생성기** (§6-1) — 검증 기준이 이미 있어 가장 확실하다
3. 인라인 해결 UI + 마감 체크리스트
4. 마스터 화면 + 이관
5. 마감 스냅샷 → 경영 보고서(§13)
