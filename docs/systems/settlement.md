## 1. 목적

신세계·CJ에서 매월 받는 원천 데이터를 업로드해 **유치원 매출 청구**와 **영업자 정산**을 자동화한다.
현재 담당자가 엑셀에서 수작업(셀 병합·수기 열 추가)으로 하는 과정을 전부 시스템화한다.

## 2. 프로세스

```
원천 업로드(신세계·CJ) → 파싱·정규화 → 영업자-유치원 매핑
  → [예외] 승인된 외부 사입·서비스 항목 합산
  → [매출] 과세/면세 분리 → 유치원 청구액
  → [정산] 마진 → 공제 → 3.3% → 영업자 지급액
  → 관리자 산출물 + 파트너별 독립 정산서 출력
```

## 3. 정산 산식 ★ (실제 엑셀 수식에서 추출, 역검증 완료)

집계 단위: **영업자 → 유치원(사업장)×식당**. 아래는 영업자별 합계 기준.

```
차액(총마진)  M = Σ(단가합계 − 원가합계)                    ← 총액(세액 포함) 기준
적립금(플랫폼) O = ROUNDUP((원가합계 − 원가세액) × 5%, -1)    ← 10원 올림
부가세차액     P = 단가세액 − 원가세액                       ← 영업자 전액 부담
사업자공제     Q = 매월 수기 입력 (커피차 등 부가서비스 비용)
지급액(세전)   R = M − O − P − Q

신고액         V = 영업자 유형에 따라 분기 ★
                 · 코파운더  → R + O   (적립금을 사업소득 신고액에 포함)
                 · 일반 파트너 → R      (신규 등록 파트너는 전부 일반)
소득세         S = ROUNDDOWN(V × 3%, -1)     ← 신고액(V) 기준, 10원 내림
지방소득세     T = ROUNDDOWN(S × 10%, -1)    ← 10원 내림
실지급         U = R − S − T                 ← 세전(R)에서 차감
```

- 총액차액 − 부가세차액 = 공급가 기준 차액 → SRS의 "공급가 기준 총마진"과 **수학적으로 동일**.
- 코파운더 3명: **김중영·이동현·조성곤**. 그 외 및 신규 등록자는 일반.
- 김중영은 과거 엑셀에서 원천징수 누락 → **시스템에서는 동일하게 원천징수 적용**.

## 4. 분할 신고

한 영업자의 사업소득을 **여러 명 명의로 나눠 신고**하는 운영을 지원한다.
- 배분은 **수기 입력**(성명 + 금액).
- **검증 필수**: 분할 합계 == 해당 영업자 신고액(V). 불일치 시 마감 차단.
- 실제 사례(26년 6월): 이동현 13,490,317 → 이동현 4,490,317 + 김인순 5,000,000 + 이유나 4,000,000.

## 5. 원천 데이터 구조

**매월 받는 파일 3종** (2026-07-31부터). 셋 다 한 번에 올린다.

| 파일 | 단위 | 담고 있는 것 |
|---|---|---|
| 신세계 `신세계_전체 일반` | 품목 | 원가 + 단가, 입고일자 |
| CJ `CJ_전체 집계표` | 사업장×식당 | **원가** + 단가 (날짜 없음) |
| CJ 거래명세서 | 품목 | **단가만**, 날짜 있음 (§5-2) |

**신세계** (`신세계_전체 일반`, 536행) — 품목 단위, **2행 병합 헤더**
```
순번 | 사업장(코드,명) | 식당(코드,명) | 입고일자 | 카테고리 | 품목코드 | 품목명 | 규격 | 단위 | 면과세 | 수량
     | 납품(단가,금액,세액,총액)   ← 원가(매입)
     | 가맹점(단가,금액,세액,총금액) ← 유치원 청구(매출)
```

**CJ** (`CJ_전체 집계표`, 40행) — 사업장×식당 집계 단위, 1행 헤더
```
번호 | 사업장코드 | 사업장 | 식당코드 | 식당명 | 사업부 | 팀
   | 원가: 과세공급가, 과세부가세, 과세금액, 면세, 합계(a)
   | 단가: 과세공급가, 과세부가세, 과세금액, 면세, 합계(b)
   | 차액(b−a)
```

⚠️ **레벨이 다름** — 신세계는 품목, CJ는 집계. 공통 정규화 지점은 **사업장×식당×과세구분**.
신세계 품목 데이터는 이 레벨로 집계해서 CJ와 합산한다.

### 5-1. 사업장 = 유치원 1곳, 식당 = 품목 ★ (2026-07-30 실측)

양쪽 원천의 **의미가 같다.** 이게 전체 데이터 모델의 기준점이다.

| 원천 | 사업장 | 식당 |
|---|---|---|
| 신세계 | `[89890] EDU)키즈_국제유치원(키즈웰)` = 유치원 1곳 | `급식재료`, `교사식재료`, `종일반간식`, `오전간식`, `행사` |
| CJ | `[1005] 키즈웰에듀푸드(해밀유치원)` = 유치원 1곳 | `…(해밀유치원)`, `…_급식재료`, `…_간식보조금` |

- 신세계 4 사업장(본사 포함) + CJ 13 사업장 = **본사 1 + 유치원 16** → 홈택스 파일의 16곳과 정확히 일치
- CJ 식당명은 유치원명을 반복해서 담고 있을 뿐, 구분자는 접미사다
- **따라서**: 사업자등록번호·상호 등 계산서 정보는 **사업장(=유치원)** 에 붙이고,
  품목명은 **식당** 에 붙인다. 별도 유치원 테이블은 필요 없다.
- 한 유치원이 두 원천에 걸치는 경우는 26년 6월에 없다. 생기면 **사업자번호로 묶어**
  계산서를 합친다 — (source, business_code)로 묶으면 안 된다.

### 5-2. CJ 거래명세서 — 집계표와 **함께** 받는다 (2026-07-31 결정)

§5에 "CJ는 집계 단위"라고만 적혀 있었으나, 그건 `CJ_전체 집계표` 이야기다.
**별도 파일인 거래명세서에는 날짜·품목이 다 있다.**

```
번호 | 사업장명 | 식당명 | 구분 | 상품코드 | 상품명 | 원산지 | 단위
   | 주문량 | 단가 | 과세 | 비과세 | 공급가 | 부가세 | 총합계
```

- 단일 시트(`SHEET1`). 맨 위 **총계** 행, 그 아래 날짜별 **소계** 행(`2026-07-01 소계`)과
  품목 행이 섞여 있다. **날짜는 품목 행에 없다** — 직전 소계에서 이어받는다.
- ⚠️ **금액은 원가가 아니라 단가(유치원 청구)다.** 26년 7월분을 사업장×식당으로
  집계해 집계표와 대조한 결과 14 사업장·39 식당 전부 **단가 쪽과 원단위 일치**했다.
  유치원이 받아보는 문서이기 때문이다.
- ⚠️ **사업장코드·식당코드가 없다.** 이름만 있어 매핑은 이름으로 한다.

#### 거래명세서로 집계표를 대체할 수 없다 (실측)

원가가 없으면 차액 M·적립금 O·부가세차액 P가 전부 계산 불가고, 따라서
영업자 지급액이 안 나온다. **역산도 안 된다** — 26년 7월 2,006품목으로 시험했다.

계약 비율은 유치원마다 다르다 (율화 1.50 / 부산_복자 1.40 / 우현·재능·미래샘 1.35 /
아름솔·우성·가명 1.30 / 해성·천안_복자 1.25 / 복자 1.22 / 젬마·선경·해밀 1.20).

```
라인총액 ÷ 비율 → 반올림      14곳 중 0곳 원단위 일치 (오차 −13,413 ~ −402원)
단가 ÷ 비율 → 10원반올림 ×수량  14곳 중 0곳 (오차 수만 원)
```

실제 비율이 1.19813·1.34836처럼 **깨끗한 값이 아니다.** 원가는 CJ의 품목별
납품가고 단가는 별도 가격표라, 곱셈으로 복원되는 숫자가 아니다.

**→ 그래서 둘 다 받는다.** 집계표 = 원가의 유일한 출처, 거래명세서 = 품목·날짜.

#### 교차검증 (`calc/cj-cross-check.ts`)

같은 달 같은 식당이면 거래명세서 단가 합계 = 집계표 단가여야 한다. **총액만이
아니라 과세·부가세·면세를 각각** 본다 — 합이 우연히 같아도 구성이 다르면
계산서가 갈라진다(과세 47장 / 면세 41장, §6-1).

어긋나면 `errors`로 차단하고, 세 가지를 구분해 보고한다:
`amount`(금액 차이) / `missingInStatement` / `missingInSummary`(이름이 어긋났을 수 있다).

파서 자체 검증도 있다 — **품목을 다 더하면 맨 위 총계와 같아야 한다.**
한 행이라도 빠지거나 두 번 세면 여기서 드러난다.

⚠️ **거래명세서가 없으면 대조를 건너뛴다**(경고만). 26년 6월처럼 함께 받기 전
달을 다시 올릴 수 있어야 한다.

### 확정된 것 (2026-07-29)

**세전 정산액이 음수일 때 → 0 처리 + 경고.**
받을 게 없는 달이므로 신고할 사업소득도 없다고 본다. 코파운더라도 적립금을 신고액에
넣지 않는다(0 처리가 우선). 원래 음수값은 `preTaxRaw`에 보존하므로, 이월 정책이
정해지면 거기서 이어가면 된다. 조용히 0으로 만들지 않고 반드시 경고를 남긴다.

**정산 대상이 아닌 사업장(본사 등) → 명시적 `정산제외` 표시.**
매핑 누락과 반드시 구분한다 — 섞이면 "마감 전 매핑 누락 없음" 검증이 무의미해진다.

### `사업소득 신고내역` 시트의 다른 정의 두 개 (2026-07-30 실측)

지급명세서는 `집계표_정산용`과 **열 이름이 같아도 값이 다르다.** 두 문서를 나란히
놓고 대조할 때 반드시 알고 있어야 한다.

1. **세액을 명의별로 계산한다.** 영업자 전체 신고액(V)이 아니라 분할된 각 명의의
   금액에 3%/10%를 적용한다 — 실제로 각 사람 앞으로 원천징수되기 때문이다.
   10원 내림을 명의별로 하므로 **합계가 전체 기준과 어긋날 수 있다**(경고로 알린다).
   26년 6월 이동현은 우연히 일치했다 (명의별 합 445,170 = 전체 기준 445,170).
2. **이 시트의 `실지급액` = 사업소득액 − 소득세계.** 집계표의 실지급(U)은
   `세전(R) − 소득세 − 지방세`라서 값이 다르다. 조성곤 예: 신고내역 1,173,955 vs
   집계표 971,215. 신고 문서이므로 신고액에서 세금만 뺀 금액을 적는다.

대조 결과: 원본 5개 행(김인순·이유나·이동현·조성곤·김영수) + 계 행 전 항목 일치.
**김중영은 원본 신고내역에 없다** — 집계표에서 원천징수가 누락된 것과 같은 원인이다.
확정 규칙대로 채우면 8,715,637원(소득세계 287,600 / 실지급 8,428,037)이 된다.
