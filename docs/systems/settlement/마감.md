# 월 마감 (§8)

> 정산 시스템 상세 — **필요할 때만 연다.** 개요·산식은 `../settlement.md`.
> ⚠️ 섹션 번호는 코드 주석(`docs §8-2` 등)이 참조하므로 **바꾸지 않는다.**

## 8. 월 마감 ★ (2026-07-30 구현 완료)

상태: `작성중(draft) → 확정(confirmed) → 마감(closed)`.
코드에서는 영어 값을 쓴다 — 한글 문자열 비교는 인코딩 사고가 나기 쉽다.

**저장하면 그 달의 상태를 통째로 굳힌다.** 담당 영업자·수수료율·유형·공제·분할신고까지
스냅샷에 들어간다. 나중에 담당자를 바꿔도 마감된 달의 내역서는 달라지지 않는다.

**재저장은 덮어쓰지 않고 새 리비전을 쌓는다** (append-only). 마감 후 수정도 이력이
남는다 — 리비전 2번째부터는 **이유를 필수로 받는다.**

확정·마감 **시각은 처음 도달한 때**를 남긴다. 재저장할 때마다 갱신하면
"언제 마감했나"를 답할 수 없다.

### 마감 전 게이트 4개 (확정·마감 모두 **서버에서 다시 검사**)

```
□ 담당 영업자 미배정 0건
□ 유치원 사업자 정보 완비
□ 식당 품목명 지정 완료
□ 분할 신고 합계 일치
```

화면이 이미 막고 있지만 서버도 재검사한다 — 깨진 상태를 스냅샷으로 굳히면
나중에 그게 "확정된 사실"이 되어버린다.

### 테이블 (migration 053)

| 테이블 | 역할 |
|---|---|
| `settlement_closings` | 월별 상태 + 헤드라인 합계 (경영 보고서 목록용) |
| `settlement_closing_snapshots` | **append-only 이력.** 전체 상태 jsonb |
| `settlement_closing_venues` | 식당 단위 flat facts (현재 리비전만) |
| `settlement_closing_partners` | 영업자 단위 산식 결과 (현재 리비전만) |

두 층으로 나눈 이유: 스냅샷 jsonb는 **재현**이 목적이라 스키마가 바뀌어도 읽을 수
있어야 하고, flat facts는 **질의**가 목적이라 정규 컬럼이 필요하다 (§13 경영 보고서).

⚠️ `partner_name`을 함께 굳히고 **FK를 걸지 않는다.** 영업자 이름이 바뀌거나
삭제돼도 마감 문서는 그대로여야 한다.

⚠️ `vatDiffGap`은 저장하지 않는다 — 항상 `vatDiff − vatPayable`로 나오는 파생값이다.
컬럼으로 두면 둘이 어긋날 수 있다.

**실DB 검증 (2026-07-30)**: 잘못된 기간 거절 / 확정→마감→재저장 리비전 1·2·3 /
확정·마감 시각 유지 / 이력 3건 / flat facts 재저장 시 중복 없음 / CASCADE 삭제.

영업이익 6,795,817 · 부가세 905,007 · 대조차 905 전부 일치.

## 8-1. 마감 잠금과 해제 (2026-07-31 구현)

**두 단계로 나눈 이유.** 확정하면 보고서·계산서는 나오는데 금액은 아직 고칠 수 있어야
한다 — 세무사 확인이 며칠 걸린다. 그래서 `확정`과 `마감`을 갈랐다.

```
draft ──confirm──▶ confirmed ──close──▶ closed
                       ▲                   │
                       └──── reopen ───────┘   (admin만, 사유 필수)
```

| 상태 | 산출물 | 금액 수정 |
|---|---|---|
| `draft` | — | 자유 |
| `confirmed` | 보고서·계산서·내역서 | **가능** (리비전이 쌓인다) |
| `closed` | 전부 | **불가** |

**마감 상태에서는 저장 자체를 거부한다** (`closingTransition`). 화면도 공제·분할
입력을 잠그지만 **경계는 `data/closing.ts`**다 — 화면을 우회해도 막힌다.

### 해제

`PATCH /api/settlement/closing` — `requireApiAdmin()`. 마감은 "이 숫자로 세무·지급이
끝났다"는 선언이라 일반 저장으로는 못 바꾼다. 경로 자체를 POST와 분리해 실수로 섞이지
않게 했다.

- **사유 필수.** 빈 문자열이면 거부한다.
- `closed → confirmed`로만 간다. 확정 상태를 또 해제하는 건 거부한다.
- **`closed_at`은 지우지 않는다.** "언제 처음 마감했나"가 지급·세무의 기준 시점이다.
- `reopen_count`가 오르고, 스냅샷 이력에 `action='reopen'` 줄이 쌓인다.
  화면 상단에 `마감 해제 N회` 배지가 붙는다.

⚠️ **수금·지급(§9)은 마감 후에도 계속 입력한다.** 현금은 마감 뒤에 들어오기 때문이다.
잠그는 건 발생(청구) 쪽 금액뿐이다.

## 8-2. 확정·마감된 달의 산출물 다시 받기 (2026-07-31 구현)

### 무엇이 문제였나

다운로드가 **업로드 화면에만** 있었다. 브라우저를 닫았다 열면 분석 결과가 사라져
계산서도 내역서도 받을 수 없었다 — 마감을 다 해 놓고도 파일을 못 받는다.

더 나쁜 건 원천 파일을 다시 올렸을 때다. 그사이 마스터(담당자·수수료율·품목명)가
바뀌었으면 **마감 당시와 다른 파일이 나온다.** 세무사에게 이미 보낸 것과 다르면
그때부터 어느 쪽이 맞는지 알 수 없다.

### 해결

```
GET /api/settlement/invoice?period=2026-06&kind=taxable|exempt
GET /api/settlement/report?period=2026-06
```

**스냅샷에서만 만든다.** 원천 파일도 마스터도 읽지 않는다.

| 산출물 | 근거 |
|---|---|
| 계산서 | 스냅샷 `invoiceRows` + `issuer` 그대로 |
| 내역서 집계표 | `closingVenues` + `closingPartners` → `rebuildClosingBlocks()` |
| 사업자공제 상세 | 스냅샷 `deductionItems` |
| 사업소득 신고내역 | `closingPartners.declared` + 스냅샷 `splits` |

⚠️ **금액을 다시 계산하지 않는다.** `rebuildClosingBlocks()`는 저장된 숫자를 시트
모양으로 옮기기만 한다. 산식으로 다시 돌리면 수수료율이 바뀐 뒤에 과거 내역서가
달라진다 — 마감의 존재 이유가 무너진다.

작성일자도 **기간의 말일**로 고정한다. 업로드 화면에서는 사용자가 연월을 골랐지만,
여기서는 `period`가 곧 답이다.

### 26년 6월 실측 대조 (업로드 vs 스냅샷)

```
집계표_정산용        다른 셀 0개  (병합 16 = 16)
사업자공제 상세      다른 셀 0개
사업소득 신고내역    다른 셀 0개
최종 엑셀            52,352바이트 = 52,352바이트
```

계산서는 12셀이 달랐는데 **원인이 명확하다** — 6월 스냅샷은 2026-07-30에
저장됐고 원단위 절사(§6-2)는 그다음 날 배포됐다. 스냅샷이 절사 이전 값을 담고 있는
것이며, 산출물 재생성 로직의 문제가 아니다. 절사를 반영하려면 **정산 화면에서 다시
확정**하면 된다.

### 파일명

POST(업로드)와 GET(스냅샷)이 **같은 이름 규칙**을 쓴다 (`invoiceResponse()` ·
`reportResponse()`로 공통화). 두 경로에서 이름이 다르면 같은 달 파일이 두 종류로
돌아다닌다.

## 8-3. 마감 메모 (2026-07-31 구현)

`settlement_closings.note` — 그 리비전이 무엇인지 사람에게 설명하는 한 줄.
경영 보고서 상단에 노란 배너로 뜬다. 지금은 **테스트 마감 표시**에 쓴다.

### ★ 재확정하면 비워진다

`saveClosing`의 upsert에 `note`를 **반드시 명시**한다. 빼면 안 된다.

실DB로 확인한 사실: upsert에서 컬럼을 생략하면 기존 값이 그대로 남는다.
리비전이 1 → 2로 올라가도 메모가 따라온다. 그러면 `테스트 마감` 딱지가
**진짜 마감에 영원히 붙는다.** 정확히 반대 효과다.

메모는 **그 리비전에 대한 설명**이므로 리비전이 바뀌면 무효다. 그래서
`note: input.note ?? null`로 항상 덮어쓴다. API 라우트는 `note`를 넘기지
않으므로, 화면에서 확정하면 자동으로 비워진다.

### 왜 화면에 표시하는가

컬럼은 migration 053부터 있었지만 **아무도 읽지 않았다.** 기록해도 보이지
않으면 없는 것과 같다 — 테스트 자료를 실제 장부로 착각하게 된다.

### 검증 (실DB 왕복)

| 단계 | 결과 |
|---|---|
| 메모를 붙여 확정 | rev 1 / `테스트 마감` ✅ |
| 메모 없이 재확정 | rev 2 / `null` ✅ |
| 마감 | rev 3 / closed / `null` ✅ |
