# 마스터 데이터와 신규 등록·이관 (§10, §14)

> 정산 시스템 상세 — **필요할 때만 연다.** 개요·산식은 `../settlement.md`.
> ⚠️ 섹션 번호는 코드 주석(`docs §8-2` 등)이 참조하므로 **바꾸지 않는다.**

## 10. 마스터 데이터

- `영업자`: 이름, **유형(코파운더/일반)**, **개인/사업자 구분**, 기본 수수료율(5%, 개별 설정 가능), 연락처
  - 수수료율 **월별 이력** 관리 여부는 미결
- `유치원(사업장)`: 사업장코드, 상호, 사업자등록번호, 대표자, 주소, 이메일, **담당 영업자 ID**
- 매핑 키: 원천 데이터의 **사업장 코드**

## 14. 신규 등록·수정·이관 (설계 — 2026-07-30)

매월 신세계·CJ 데이터로 정산을 시작할 때 **신규 유치원·신규 식당·신규 영업자**가
나타난다. 담당 이관도 생긴다. 이 절차가 무너지면 금액이 조용히 빠지거나
과거 정산이 재현되지 않는다.

### 14-1. 절대 원칙 — 과거 정산은 바뀌지 않는다

지난달 내역서를 다시 뽑았을 때 담당자나 금액이 달라지면 **지급 근거와 세무 문서가
흔들린다.** 두 가지로 막는다.

1. **월 마감 스냅샷.** 마감 시점의 매핑·영업자 유형·수수료율·사업자공제·분할신고를
   통째로 저장한다. 마감된 월은 현재 마스터가 아니라 **스냅샷으로 재생성**한다.
2. **이관은 월 단위로만.** 원천 데이터가 월 집계라 일할 계산이 불가능하다.
   `적용 시작월(YYYY-MM)`만 받는다. 월 중간 이관 개념은 두지 않는다.

### 14-2. 마감 차단 사유 3종 (매핑 누락과 같은 급)

| 사유 | 왜 막는가 |
|---|---|
| **담당 영업자 미배정** | 그 사업장 금액이 정산에서 조용히 빠진다 |
| **유치원 사업자 정보 미비** | 계산서를 발행할 수 없다 (사업자번호·상호·대표자·주소·이메일) |
| **식당 품목명 미지정** | 계산서 발행 단위(유치원×품목×과세구분)를 정할 수 없다 |

`정산 제외`는 이 셋과 **명시적으로 구분한다** (§11 확정 사항). 본사 마케팅비처럼
의도적으로 빼는 것은 경고를 내지 않는다.

### 14-3. 흐름 — 월 정산 안에서 인라인으로 해결한다

```
업로드 → 분석 → [미해결 항목] 그 자리에서 해결 → 자동 재분석 → 정산 → 마감(스냅샷)
```

**별도 마스터 화면으로 나가게 하지 않는다.** 담당자는 "왜 마감이 안 되지?"에서 막히고,
화면을 옮기면 맥락과 업로드한 파일을 잃는다. 파일은 이미 브라우저에 있으므로
저장 후 즉시 재분석한다.

미해결 항목 각 행에 액션 3개:
- **기존 유치원에 연결** — 같은 사업자번호의 새 식당. 담당 영업자를 자동 상속한다.
- **신규 유치원 등록** — 사업자 정보 + 담당 영업자 + 품목명
- **정산 제외** — 사유 선택(마케팅비/본사/기타)

모달이 아니라 **인라인 확장**으로 연다. 여러 건을 연속 처리해야 하므로 모달은 방해다.

### 14-4. 입력 안전장치

**사업자등록번호 — 체크섬 검증 (국세청 규칙)**

가중치 `[1,3,7,1,3,7,1,3,5]`를 앞 9자리에 곱하고, 9번째 자리 × 5의 **십의 자리를 더한** 뒤
`(10 − 합 % 10) % 10`이 마지막 자리와 같아야 한다.

실측: 우리 17개(본사 포함) **전부 통과**, 한 자리 오타 1,530가지 **100% 검출**.
국세청 진위확인 API(공공데이터포털)는 선택 사항 — 체크섬만으로 오타는 다 막힌다.

- 사업자번호가 **이미 등록돼 있으면** "복자유치원(1318208466)이 이미 있습니다 —
  같은 유치원의 다른 원천인가요?"로 유도한다.
- ⚠️ 상호 중복은 **정상**이다 (`복자유치원` 3곳). 중복 판정은 사업자번호로만 한다.
- 사업자번호 **변경은 수정이 아니라 신규 등록 + 이관**으로 안내한다. 사실상 다른 사업자다.

**품목명 — 오타가 계산서를 쪼갠다**

기존 23종을 빈도순 콤보로 제시한다 (`급식재료` 27건, `방과후간식` 20건이 압도적).
직접 입력은 허용하되 유사 항목을 경고한다: `급식재료 `(뒤 공백)을 넣으면
"기존 `급식재료`와 다릅니다 — 계산서가 2장으로 쪼개집니다".

**신규 영업자**

유치원 등록 폼 안에서 바로 만들 수 있게 한다(`+ 새 영업자`). 단:
- **유형은 `일반` 고정** (§3: 신규 등록 파트너는 전부 일반)
- 수수료율 5% 기본
- **코파운더 지정·수수료율 변경은 마스터 화면에서만** — 금액에 직결되므로 실수를 막는다

### 14-4-1. 구현 완료 (2026-07-30)

`app/app/settlement/pending-panel.tsx` + `POST /api/settlement/master`

- 체크리스트 4항목이 모두 통과하면 카드가 **초록 확인 카드로 바뀐다**. 남아 있으면
  각 항목이 인라인 폼으로 펼쳐진다. 번호를 붙이지 않았다 — 단계가 아니라 게이트다.
- 저장 후 **자동 재분석**한다. 이때 사업자공제·분할신고 입력은 **보존한다**
  (`analyze({ keepInputs: true })`) — 방금 입력한 값이 날아가면 안 된다.
- 사업자번호는 입력 즉시 체크섬으로 검증하고, **서버에서 다시 검증한다.**
  계산서에 그대로 찍히는 값이므로 클라이언트 값을 믿지 않는다.
- 품목명은 기존 값을 `datalist`로 제시하고, 공백만 다른 유사 이름을 경고한다 —
  오타로 새 품목이 생기면 계산서가 두 장으로 쪼개진다.
- **2026-08-31 개선:** 미지정 품목명은 원본 식당명에서 접미사를 추출해 추천값으로
  미리 채우되 자동 저장하지 않는다. 드롭다운 후보는 전체 마스터가 아니라
  **같은 공급사·같은 사업장코드(유치원)** 의 기존 품목명만 보여주며, 같은
  과세구분을 먼저 배치한다. 다른 유치원의 품목명이 섞여 잘못 확정되는 것을 막는다.
- 신규 영업자는 폼 안에서 만들 수 있고 **유형은 `일반` 고정**이다 (§3).
  코파운더 지정은 금액(신고액 V)에 직결되므로 여기서 할 수 없다.

⚠️ **계산서 정보 갱신은 `update-invoice`로 UPDATE한다.** `assign-venue`의 upsert를
쓰면 담당 영업자를 함께 보내야 하고, 실수로 빠지면 매핑이 지워져 그 사업장 금액이
조용히 정산에서 빠진다.

⚠️ **정산 제외는 사유를 필수로 받는다.** 사유 없이 제외만 되어 있으면 다음 담당자가
왜 빠졌는지 알 수 없고 실수로 되살린다.

### 14-5. 이관 UI

- 진입점: 유치원 상세 또는 영업자 상세의 `담당 이관`
- 대상 유치원 다중 선택 → 새 담당자 → **적용 시작월**(기본: 다음 달)
- **이번 달로 소급하면 금액 영향을 미리 보여준다** — "A 실지급 −1,234,560 / B +1,234,560"
- 이미 마감된 월은 소급 불가. 재개 권한이 있어야 열 수 있다 (§8).
- 이관 이력을 유치원 상세에 타임라인으로 남긴다

### 14-6. 마스터 수정

유치원 정보는 **계산서에 그대로 찍힌다.** 변경 시 "다음 발행부터 적용됩니다"를 명시하고,
누가·언제·무엇을·이전값을 이력으로 남긴다 — 세금계산서 오류는 수정발행 사유가 되므로
추적이 필요하다.

### 14-7. 마감 전 체크리스트 (게이트)

```
□ 담당 영업자 미배정          0건
□ 유치원 사업자 정보 완비      (사업자번호·상호·대표자·주소·이메일)
□ 식당 품목명 지정 완료
□ 분할 신고 합계 일치
```

4개 전부 통과해야 `확정` → `마감`. 각 항목에서 해당 위치로 바로 점프할 수 있게 한다.

### 14-8. 스키마 (051/052 적용 완료 — 2026-07-30)

- `settlement_venues`(=사업장=유치원)에 계산서 정보 추가: `company_name`, `biz_type`,
  `biz_item`, `email2`, `exclusion_reason`. `biz_reg_no`는 050에 이미 있고
  `CHECK (~ '^[0-9]{10}$')`로 형식을 막는다. 체크섬은 앱에서(`isValidBizRegNo`).
- `settlement_issuer` — 계산서 공급자(본사) 단일 행. `settlement_venues`의 본사 행을
  재활용하지 않는다: 그쪽은 공급받는자를 담는 테이블이라 의미가 섞인다.
- `settlement_venue_items`(=식당) — 키가
  `(source, business_code, restaurant_code, **tax_kind**)` 다.
  ⚠️ **과세구분이 키에 들어가는 이유**: 같은 식당이 과세·면세에서 품목명이 다를 수 있다.
  26년 6월 나래유치원 식당 `원아급간식` — 과세 `원아급간식` / 면세 `급식재료`.
  하나로 합치면 계산서 품목명이 틀린다.

**시드는 손으로 옮기지 않는다.** `scripts/generate-invoice-seed.ts`가 052 파일을 직접
생성한다 — 실제로 손으로 베꼈다가 주소 9곳과 식당코드 다수를 틀렸고, 생성 파일과
대조해서야 잡았다.

시드 검증 (스크립트가 매번 재확인): 사업장→유치원 16/16 유일 식별 /
식당×과세구분→품목 87건 유일 + 합산 2건 = 89건 / 과세 33,182,420·면세 65,846,245
원단위 일치 / 미청구 계산서 0장 / 사업자번호 16곳 체크섬 통과
- `settlement_partner_transfers`: 유치원 × 이전 담당 × 새 담당 × `effective_from`(YYYY-MM)
- `settlement_closings` + 스냅샷 테이블: 마감 월의 전체 상태
