# 품목 단위 조정

> 정산 시스템 상세 — **필요할 때만 연다.** 개요·산식은 `../settlement.md`.
> ⚠️ 섹션 번호는 코드 주석(`docs §18` 등)이 참조하므로 **바꾸지 않는다.**

## 18. 품목 조정 — 정산제외·식당 이동 (2026-07-31 구현)

영업파트너가 일부 품목을 **본인 부담**으로 처리해 달라고 요청하는 일이 매달 있다.
그 품목을 유치원 청구에서 빼고, 부담을 그 파트너에게 지운다.

### 왜 원천을 고치지 않는가

**CJ 집계표가 먼저 확정된 뒤에 요청이 온다.** 집계표를 매번 재발행받으면

- 마감이 CJ 일정에 묶인다
- 재발행본이 거래명세서와 또 어긋나 교차검증(§5-2)이 깨진다
- "CJ가 이렇게 청구했다"는 사실이 사라진다

그래서 **원천은 사실 그대로 두고, 조정을 우리 쪽 기록으로 얹는다.**
원본과 우리 판단이 둘 다 남아, 나중에 세무 질의가 와도 답할 수 있다.

### 적용 순서 ★

```
원천 대조(무결성, §5-2) → 조정 적용(정책, §18) → 매핑 → 정산 산식
```

교차검증은 **조정 전** 숫자로 한다. 원천은 사실이고 조정은 정책이라,
섞으면 "CJ가 틀린 것"과 "우리가 뺀 것"을 구분할 수 없다.

### 단가에서만 뺀다 — 원가는 손대지 않는다

품목별 원가를 알 수 없고(역산 14곳 중 0곳 일치, §5-2), 물건은 이미 납품돼
원가는 CJ에 그대로 나간다. 그 결과가 요건과 정확히 맞는다.

```
단가 −X  → 차액 M −X   → 영업파트너가 부담   ✓
원가 불변 → 적립금 O 불변 → 본사는 부담 안 함  ✓
```

**과세 품목이면 부가세도 함께 빠진다.** `P = 단가세액 − 원가세액`이 같이 줄어
`R = M − O − P − Q`에서 상쇄되므로, **파트너 부담은 정확히 공급가 X**다.

```
단가 총액 −1.1X → M −1.1X
단가 세액 −0.1X → P −0.1X
R = (M−1.1X) − O − (P−0.1X) − Q = R − X
```

유치원에서 받지 않으니 납부할 부가세도 없어 결과가 맞는다.

⚠️ **CJ가 반품 크레딧을 주는 경우는 지원하지 않는다.** 그때는 원가도 줄어야 하는데
품목별 원가를 모른다. 크레딧 금액을 별도로 받아야 한다.

### 두 가지 처리

| 종류 | 무엇 | 사업장 합계 | 정산 총액 |
|---|---|---|---|
| `exclude` 정산 제외 | 유치원에 청구하지 않는다 | 줄어든다 | 줄어든다 |
| `move` 식당 이동 | 같은 사업장의 다른 식당으로 옮긴다 | **불변** | **불변** |

이동은 계산서의 **품목 줄 구성**만 바꾼다(급식재료 ↓, 방과후간식 ↑).
유치원 예산이 갈려 있어서 필요한 처리다.

⚠️ 이동 대상은 **그 달에 실적이 있는 식당**만 고를 수 있다. 없는 식당을 만들려면
식당코드와 계산서 품목명이 필요한데 거래명세서에는 둘 다 없다.

### 금액 계산 (`calc/adjustment.ts`)

**전량이면 원천 라인 금액을 그대로 쓴다.** 곱셈으로 다시 만들면 반올림 오차가
생길 수 있는데, 전량 조정에서 1원이라도 남으면 안 된다.

부분이면 `단가 × 수량`이다. 26년 7월 실측 근거:

```
단가 × 주문량 = 공급가        2,006행 전부 일치 → 부분 조정이 원단위로 정확
부가세 = 과세공급가 ÷ 10      어긋난 행 0건 (과세공급가는 늘 10의 배수)
한 행은 과세 아니면 면세       둘 다 가진 행 0건
소수 수량(KG)                46행 → 소수 허용, 금액은 10원 단위로 맞춘다
```

### 품목을 가리키는 키

`(사업장명, 식당명, 날짜, 상품코드)` — 26년 7월 2,006개 조합에 **중복 0건**.

⚠️ 거래명세서에는 **사업장코드·식당코드가 없어** 이름으로 잡는다 (§5-2).
CJ가 이름을 바꾸면 조정이 원천을 못 찾고, 그때는 오류로 막는다.

### 오류가 하나라도 있으면 전부 반영하지 않는다

일부만 반영하면 화면 숫자가 "고치다 만 상태"가 되고, 그게 맞는 값인지
사용자가 판단할 수 없다. 막는 경우:

- 거래명세서에서 품목을 못 찾음 (파일이 바뀌었거나 다른 달)
- 조정 수량이 원천을 넘음 (같은 품목에 여러 건이면 **합계**로 본다)
- 제외·이동 대상 식당이 집계표에 없음

### 화면 (`adjustment-panel.tsx`, 3번 섹션)

**금액을 손으로 치지 않는다.** 거래명세서 품목을 검색해 고르면 날짜·상품코드·
단가·과세구분이 전부 따라온다. 사람이 넣는 건 수량뿐이다 (요청자·사유는 §18-3에서
기본값으로 채워 준다).

- 검색은 띄어쓰기로 조건을 겹친다 (`07-06 순두부`) — 요청이 그렇게 온다
- 저장 전에 **빠질 금액을 미리 보여준다**
- 목록은 **항상 펼쳐 둔다.** 조정을 빠뜨리면 그냥 청구되므로 접으면 안 된다
- 사유·요청자는 **필수**. 없으면 나중에 아무도 설명 못 한다 — 그래서 §18-3에서
  기본값을 채워 준다
- 수정은 없다 — 지우고 다시 넣는다. "금액을 슬쩍 고친 것"과 "뺐다가 되돌린 것"은
  다른 사건이라 이력이 갈려야 한다

### 18-3. 입력은 채워서 준다 (2026-08-01)

**빈 칸을 안내문으로 채우지 않는다.** 요청자·사유가 비어 있으면 저장 버튼이
비활성인데, 회색 안내문(`김영수`, `정산제외 요청(본인부담)`)이 떠 있어 **이미
입력된 것처럼 보였다.** 눌러도 아무 일이 없고 이유도 안 보였다 — 실제로 여기서 막혔다.

품목을 고르면 이렇게 채워진다. 전부 그 자리에서 고칠 수 있다.

| 칸 | 기본값 |
|---|---|
| 수량 | 원천 전량 |
| 요청자 | **그 유치원 담당 영업자** (`closingVenues`의 `partnerName`) |
| 사유 | 제외면 `정산제외 요청(본인부담)`, 이동이면 `식당 이동 요청` |

- 손으로 고친 칸은 기본값이 **덮어쓰지 않는다.** 처리 종류를 바꿨다고 방금 적은
  사유가 날아가면 안 된다
- 담당 영업자를 찾는 키는 `adjustmentVenueKey` — **반영 로직과 같은 함수**를 쓴다.
  규칙이 갈리면 엉뚱한 사람이 요청자로 들어간다 (테스트로 고정)
- 그래도 못 누를 때는 **이유를 버튼 옆에 적는다** (`수량이 원천을 넘습니다` 등)

저장 후에는 폼을 닫지 않는다. 조정은 말일 다섯 시간에 몰려 오므로 품목만 비워
다음 건을 바로 받고, **방금 저장한 줄을 목록에서 노란색으로** 표시한다.

## 19. 유치원 제공 거래명세표 (2026-08-01 구현)

신세계 유치원에 보내는 **청구 명세 문서**. 국제유치원이 신세계에서 받고 있는
양식을 실측해 만들었다.

### 근거 — 우리 원천으로 만들 수 있다

`국제 26년 6월 급식 청구서류(거래명세표).xlsx`와 우리 원천을 대조했다.

```
품목·규격·단위·수량·단가   전부 일치 (6/1 급식재료 14건 전수 확인)
집계표 계 행              8,897,920 / 889,792 / 16,401,559 / 26,189,271  원단위 일치
6/1 일자 합계             과세 20,460 / 부가세 2,046 / 면세 765,500 → 788,006  일치
```

### 구성

```
집계표      식당별 공급가(A) / 부가세(B) / 계 / 면세(C) / 합계액(A+B+C) + 계 행
<식당명>    일자별 명세 — 품목표 + 그날 합계(과세·면세), 맨 끝 월합계
조정 내역   있을 때만 (§18)
```

- **금액은 가맹점(단가) 기준**이다 — 유치원 청구가. 우리 매입가(원가)는 담지 않는다.
- **유치원마다 파일을 따로** 만든다. 한 파일에 여러 곳을 담으면 다른 유치원 단가가 섞인다.
- **정산 제외 사업장(본사)은 목록에 안 나온다.**
- 기간 검증(§8-4)에 걸리면 생성도 막는다 — 잘못된 달 명세표를 유치원에 주면 안 된다.

### 온도는 품목명에서 뽑는다

원천에 온도 열이 없다. 대신 품목명이 `노랑 파프리카 국내산 냉장`,
`세척당근 국내산 실온(냉장 권장)`처럼 **온도로 끝난다** (26년 6월 실측).
못 찾으면 빈칸으로 둔다.

### ⚠️ 원산지 열은 만들지 않는다

신세계 원본에는 `원료 국내산 ,소금 중국산`, `중국, 페루, 미국`처럼 **상세 원산지**가
있는데 우리 원천에는 그 열이 없다. 품목명의 `국내산` 정도로 흉내 내면
**틀린 원산지를 유치원에 주는 문서**가 된다. 그래서 아예 만들지 않는다.

원산지를 넣으려면 신세계에서 원산지 열이 있는 원천을 받아야 한다.

### 서식

내용이 통하는 수준까지만 맞춘다. 신세계 원본은 43열에 셀 병합으로 공급자 박스를
그려 놨는데, 테두리·배경까지 재현하려면 SheetJS 유료 기능이 필요하다.
유치원이 확인할 것은 **어느 날 무엇이 얼마에 들어왔는가**다.

### CJ 유치원은 만들 수 없다

CJ는 집계표만 받아 품목이 없다. 거래명세서(§5-2)가 있지만 그건 **CJ가 이미
유치원에 주는 문서**라 우리가 다시 만들 필요가 없다.

## 19-2. 신세계 원본 서식 그대로 (2026-08-01)

§19의 단순 표를 **원본 폼 그대로**로 바꿨다. 유치원이 신세계에서 받던 문서를
그대로 원한다.

### 공급자는 (주)신세계푸드다 — 바꾸지 않는다

우리 단가가 신세계 청구가와 **원단위로 같음을 확인**했으므로 사실과 어긋나지 않는다.

```
국제유치원 26년 6월   우리 단가        신세계 원본
  공급가(A)          8,897,920       8,897,920   ✓
  부가세(B)            889,792         889,792   ✓
  면세(C)           16,401,559      16,401,559   ✓
  합계액            26,189,271      26,189,271   ✓
  식당 5개 각 행도 전부 일치
```

공급자 정보와 직인 이미지는 **템플릿 파일에 박혀 있고** 코드가 건드리지 않는다.

### 왜 템플릿인가 — 코드로 그릴 수 없다

```
시트 6개 · 열 43개(폭 0.1~9.4의 미세 열로 칸을 그림)
배송일 블록 66개 · 병합 7,309개 · 급식재료 시트만 942행
```

`exceljs`로 실험해 확인했다.

```
왕복 저장   병합 430 / 테두리 571셀 / 채움 49 / 글꼴 80 / 열너비·행높이  전부 보존
블록 복제   테두리 571 / 병합 70 / 값 65   원본 블록과 동일
도장 이미지 18 → 19개  복제됨
```

### 블록 = 33행

머리(1~16) + 품목 1행 + 꼬리(18~33). 품목이 N건이면 `33 + (N-1)`행.
⚠️ 34로 잡으면 블록마다 1행씩 밀린다 — 원본 제목 행이 3·36·69로 **33 간격**이다.

### 명세서는 텍스트, 집계표는 숫자

명세서 시트는 **모든 셀이 `@`(텍스트) 서식**이다. 신세계 시스템이 `'13,170'`처럼
콤마까지 문자열로 찍는다. 숫자를 넣으면 `13170`으로 보인다.
집계표만 `#,##0` 숫자 서식이라 숫자로 넣는다.

### ⚠️ 집계표 9행 병합

템플릿 9행은 `계` 행이라 `A9:B9`가 병합돼 있다. 풀지 않고 본문을 쓰면 번호(A)와
식당명(B)이 한 칸이 되어 **번호가 사라진다.** 실제로 그랬다.

| `[간납]` 접두어 | 있음 | 없음 | 우리 원천에 없다 |
| 온도 | 전부 | 일부 | 품목명이 온도로 끝나지 않으면 못 뽑는다 (`스위트청포도`) |
| 품목 순서 | 신세계 순 | 원천 순 | 금액에 영향 없음 |
| 식당명 | `행사용` | `행사` | 마스터 표기 차이 |
| 계 수식 | `SUM(C7:C12)` | `SUM(C8:C12)` | 원본이 헤더행까지 더한다 — 우리가 맞다 |

### ⚠️ 원본 이미지는 도장만 가져온다 (2026-08-01)

원본에는 `합계`·`26,340`이 **글자 그림(JPEG)** 으로 합계 칸 위에 덮여 있다.
블록을 복제하면서 그것까지 복사해 **모든 식당 시트에 오전간식 첫날 금액이
그림으로 박혔다.** 실제로 그렇게 나갔다.

- 템플릿을 뽑을 때 **머리 구간(공급자 박스)의 도장만** 남긴다
- 생성기에서도 품목·꼬리 구간 이미지를 한 번 더 버린다
- 안 쓰는 미디어 66개도 버린다 — 그 조각들이 **다른 유치원 파일 안에 남는다**
  (화면엔 안 보여도 압축을 풀면 나온다). 템플릿 156KB → 24KB, 생성물 467KB → 335KB

⚠️ **exceljs 앵커를 `{...anchor}`로 펼치면 안 된다.** `row`·`col`이 프로토타입
getter라 **복사되지 않는다.** `nativeRow`만 넘어가서 블록을 옮겨도 이미지가
제자리에 남고, 위치로 거르는 필터도 전부 빗나간다. 좌표를 먼저 읽어 숫자로 굳힌다.

### 페이지 넘김 (2026-08-03)

**날짜 하나가 인쇄 한 장이다.** 두 가지를 같이 건다.

**① 탄력 여백 행** — 월합계와 검수 사이의 빈 행(템플릿 r23)이 늘었다 줄었다 하며
블록이 한 장을 채운다. 원본이 쓰는 방식 그대로다.

```
오전간식 (품목  1건)   409.6pt
급식재료 (품목 14건)    65.2pt
→ 블록 총높이는 둘 다 819.4pt = 한 장
```

안 맞추면 품목이 많은 날 블록이 1,150pt까지 커져 **매번 두 장**이 된다.
한 장 목표는 **815pt** — 실측 819.4에 딱 맞추면 반올림 한 번에 밀린다.

**② 명시적 페이지 나눔** — 블록 끝마다 `addPageBreak()`. 행 높이가 어떻든
다음 날짜는 새 장에서 시작한다. 원본은 이게 없어 행 높이에만 의존한다.

⚠️ 마지막 블록 뒤에는 넣지 않는다 — 빈 장이 하나 더 붙는다.

**결과 (26년 6월 국제유치원 급식재료)**

```
블록 21개 중 18개가 한 장, 3개가 두 장 (품목 17·19·23건)
→ 24장.  원본도 24장이고 두 장짜리 날짜도 같다
페이지 번호도 인쇄 장수 기준으로 매긴다 (`10/24`)
```

⚠️ **이어지는 장에는 페이지 번호·검수란이 없다.** 원본은 패딩으로 첫 장을 채우고
꼬리를 한 번 더 찍는데, 그 패딩은 행 높이 자동맞춤에 달려 있어 재현하지 않았다.
