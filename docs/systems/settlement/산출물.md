## 6. 산출물 (엑셀 3종)

1. **매출 세금계산서/계산서 일괄발행** — 홈택스 업로드용. 과세→세금계산서, 면세→계산서로 분리.
   양식 수령·역검증 완료 (2026-07-30). 아래 §6-1 참고.
2. **영업자별 개별 정산 내역서** — 유치원별 매출·원가, 공제 상세, 3.3%, 실지급액
3. **사업소득 지급명세서** — 세무사 제출용. **주민번호 칸은 빈칸으로 출력**하고 사용자가 직접 채운다.

### 6-1. 홈택스 일괄발행 양식 ★ (2026-07-30 실측·역검증 완료)

근거 파일: `(세금)계산서 발행을 위한 엑셀 파일_26년 6월.xlsx`(과세),
`계산서 발행을 위한 엑셀 파일_26년 6월.xlsx`(면세) — 실제 홈택스에 올린 파일.

**공통 구조**: 1~5행 비움, **6행 헤더, 7행부터 데이터.** 시트명 `Sheet1`.
**1행 = 계산서 1장 = 품목 1건.** 품목2~4 슬롯은 쓰지 않았다.

| | 과세(세금계산서) | 면세(계산서) |
|---|---|---|
| 열 수 | 59 (BG) | 54 (BB) |
| 종류(A) | `01` 일반 | `05` 일반 |
| 공급가액합계 | T | T |
| **세액합계** | **U** | 없음 |
| 비고 | V | U |
| 품목1 블록 | W~AD (8열) | V~AB (7열) |
| 영수/청구 | BG = `02`(청구) | BB = `02`(청구) |

⚠️ **세액 열(U) 때문에 과세 파일은 U 이후 모든 열이 1칸 밀린다.** 두 양식을 같은
코드로 만들 때 오프셋을 상수로 두지 말고 양식별 열 맵을 따로 정의할 것.

- 작성일자(B) `20260630` — 월말일, 8자리 문자열
- 일자1(W/V) `30` — **2자리, 작성년월 제외**
- 공급자는 항상 본사 고정: `8310503575` / 키즈웰에듀푸드 / 김중영 / 도매 및 소매업 / 교재
- 공급받는자 업태·종목은 16곳 모두 `유치원` / `유치원`, 이메일2는 전부 미사용
- ⚠️ 원본에는 **영수/청구 열만 채워진 빈껍데기 행이 42개**(면세 20, 과세 22) 있다.
  생성기는 만들지 않는다.

**역검증 (26년 6월, 4개 항목 전부 원단위 일치)**

| 항목 | 집계표_정산용 | 홈택스 파일 |
|---|---|---|
| 과세 공급가 | 33,182,420 | 33,182,420 |
| 과세 세액 | 3,318,242 | 3,318,242 |
| 면세 금액 | 65,846,245 | 65,846,245 |
| 총 청구액 | 102,346,907 | 102,346,907 |

- 유치원 16곳 / 과세 47장 + 면세 41장 = 88장
- ⚠️ **본사(정산제외) 12,925원은 계산서 대상이 아니다.** 자기 자신에게 발행하지 않는다.
  단가합계 102,359,832 − 본사 12,925 = 102,346,907. 매출 산출은 **정산제외 사업장을 뺀다.**
- ⚠️ **`복자유치원`이라는 상호가 3곳**(사업자번호 1318208466 / 5798200308 / 3058221435)
  + `수원복자유치원` 별도. **상호는 키가 아니다. 사업자등록번호가 키다.**

**품목명은 식당명에서 기계적으로 나오지 않는다 → 마스터에 저장해야 한다**

식당명 51건 중 15건은 품목 문자열을 포함하지 않고, 포함해도 표기가 다르다:

| 식당명 | 실제 품목 |
|---|---|
| `키즈웰에듀푸드(선경유치원)` (접미사 없음) | `급식재료` |
| `키즈웰에듀푸드(젬마유치원_수익자)` | `급식재료(수익자)` |
| `키즈웰에듀푸드(부산_복자유치원_식재료(교원))` | `급식재료(교직원)` |
| `국제유치원(키즈웰) 행사` | `행사용` |
| `키즈웰에듀푸드(복자유치원_방과후간식재료)` | `방과후간식` |

⚠️ **N개 식당 → 1장으로 합산되는 경우가 있다.** 해밀유치원 과세:
`(해밀유치원)` 39,490 + `(해밀유치원_급식재료)` 96,650 = **급식재료 136,140** 1장
(세액도 3,949 + 9,665 = 13,614로 정확히 합산). 따라서 발행 단위는 식당이 아니라
**(유치원 사업자번호 × 품목 × 과세구분)** 이다.

금액 기준으로 식당→품목을 역추적하면 **89건 중 87건이 유일 매칭**되고, 남은 2건이
위 해밀 합산 사례다. 이 결과를 시드로 쓰되 사람이 한 번 검토한다.

**구현 완료 (2026-07-30)** — `features/settlement/report/invoice-sheet.ts`

실파일 대조 결과: 과세 47장 + 면세 41장 = **88장 전부**
`(사업자번호 × 품목 × 공급가 × 세액)`이 원본과 일치. 합계·장수도 전부 일치.
`scripts/generate-invoice-files.ts`가 이 검증을 재실행한다 (마스터는 DB에서 읽는다 —
시드·로더·생성기가 어긋나지 않는지 실제 런타임 경로로 확인해야 한다).

⚠️ **행 순서는 원본과 맞추지 않는다.** 원본 순서는 `집계표_정산용`의 수작업 배열을
따르고 재현할 근거가 없다. 홈택스는 **1행 = 독립 계산서**라 순서가 의미를 갖지 않으므로
집합 일치로 검증한다.

작성일자는 **월말일**이다. 화면에서 `YYYY-MM`만 받아(`<input type="month">`) 서버가
말일을 계산한다 — 자유 입력으로 두면 `26년6월` 같은 표기에서 연도·일자가 애매해진다.

### 6-3. 사업소득 지급명세서

세무사 제출용. `report/declaration-sheet.ts` — 내역서 통합 파일의 세 번째 시트로 붙는다.

- **주민번호 칸은 비워서 출력한다.** 사용자가 직접 채운다 (§7).
  우리는 저장하지도, 화면에 띄우지도 않는다.
- **본사는 들어오지 않는다.** 정산 대상이 아니므로 신고할 사업소득도 없다.
- 신고액은 `declared`를 쓴다. 세전 정산액이 음수인 달은 0으로 처리되므로
  지급명세서에도 0이 나간다 (§11 확정 사항).
- 분할 신고(§4)가 걸린 영업자는 분할된 금액으로 여러 행이 나간다.

#### ⚠️ 입력은 서버에서 되살린다 (2026-08-02)

공제·분할은 확정할 때 스냅샷에 굳지만, **화면이 다시 읽지 않아 통째로 사라졌다.**

```
분석 버튼      setDeductions({}) · setSplits({})  ← 매번 비웠다
새로고침       스냅샷에 있는데 안 읽었다
```

"저장한 자료가 계속 초기화된다"는 보고가 이것이다. 고친 내용:

- **분석은 입력을 지우지 않는다.** 이번 분석에 없는 영업자 항목만 버린다
- 정산월을 고르면 `GET /api/settlement/closing?period=`의 `inputs`로 되살린다

#### 지난달 명의 불러오기

매달 같은 사람들에게 나눠 신고한다. 처음 설정할 때 **직전 달 명의를 이어받는다.**

```
26년 6월   이동현 4,490,317 · 김인순 5,000,000 · 이유나 4,000,000   합 13,490,317
7월 신고액 10,000,000 이면
           이동현 3,328,548 · 김인순 3,706,362 · 이유나 2,965,090   합 10,000,000
```

⚠️ **금액은 그대로 가져오지 않는다.** 신고액이 달마다 다르므로 지난달 비율로 다시
나눈다. **합계는 1원도 어긋나면 안 되므로**(어긋나면 마감이 막힌다) 반올림 차액은
첫 행이 흡수한다 — `carryOverSplits`, 테스트로 고정.

⚠️ 이 절은 **2026-07-31까지 번호가 없었다.** 코드 4곳이 `docs §6-3`으로 참조하는데
문서에 그 제목이 없어 찾아갈 수 없었다. 번호를 붙이는 것으로 끊긴 참조를 이었다.

## 6-2. 공급사 원본 금액 + CJ 1016 예외 (2026-09-05 정책 변경)

기존 **10원 절사 정책은 폐기**했다. 일반 CJ·신세계 거래처는 공급사가 내려준
과세 공급가·부가세·면세 금액을 시스템이 다시 계산하거나 절사하지 않고 원단위 그대로 쓴다.

```text
최종 청구액 = 공급사 과세 공급가 + 공급사 부가세 + 공급사 면세액
```

`settlement_venues.invoice_round_down`과 `settlement_issuer.invoice_rounding_mode`는
배포 롤백 호환을 위해 한 운영기간 남기지만 런타임 계산은 완전히 무시한다.
과거 확정·마감 스냅샷은 당시 발행값을 그대로 재발급하므로 변경하지 않는다.

유일한 예외는 **CJ 사업장코드 1016(인천 복자유치원)**이다.

- 계산서 품목·과세구분별로 원본 공급가·부가세와 최종값을 나란히 저장한다.
- 담당자는 유치원 요청을 받은 뒤 최종 공급가·부가세를 직접 편집하며, 저장 즉시 반영한다.
- 공급가·부가세뿐 아니라 **총 청구액 증감도 허용**한다.
- 기존 활성값을 다시 저장하면 덮어쓰지 않고 취소 이력으로 남긴 뒤 새 최종값을 만든다.
- 저장 당시 원본과 현재 공급사 원본이 1원이라도 달라지면 오래된 조정은 적용하지 않는다.
- 면세는 부가세 0, 모든 금액은 0 이상의 원 단위 정수여야 한다.
- 파트너 정산과 공급자 원금은 공급사 원본을 유지하고, 조정 차액은 본사가 부담한다.
- 최종값은 세금계산서·계산서, CJ 유치원 청구서류, 통합 정산서, 수금대장,
  경영보고서에 동일하게 반영한다. 파트너 정산서는 원본을 유지한다.
- 이미 확정된 달을 편집한 경우 8번 월 마감에서 다시 확정하거나 마감해야 새 리비전의
  경영보고서·재발급 산출물에 반영된다. 마감 후에는 관리자 해제 전까지 편집할 수 없다.

원장은 `settlement_invoice_overrides`에 보존하고, 마감 스냅샷(version 5)에도 함께 굳힌다.
